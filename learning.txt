--creation of catalog for a project 

How to build this from scratch in any project

The pattern is always:

Create a Spark session with metastore + warehouse support.
Write your data as Delta/Parquet files to a stable path.
Create a database/schema like bronze.
Register tables pointing to those paths.
Always reopen Spark with the same metastore config.
Minimal example:

spark = (
    SparkSession.builder
    .appName("MyProject")
    .config("spark.sql.extensions", "io.delta.sql.DeltaSparkSessionExtension")
    .config("spark.sql.catalog.spark_catalog", "org.apache.spark.sql.delta.catalog.DeltaCatalog")
    .config("spark.sql.warehouse.dir", "/app/spark-warehouse")
    .config("javax.jdo.option.ConnectionURL", "jdbc:derby:;databaseName=/app/metastore_db;create=true")
    .enableHiveSupport()
    .getOrCreate()
)

df.write.format("delta").mode("overwrite").save("/app/data/bronze/customers")

spark.sql("CREATE DATABASE IF NOT EXISTS bronze")
spark.sql("""
    CREATE TABLE IF NOT EXISTS bronze.customers
    USING DELTA
    LOCATION '/app/data/bronze/customers'
""")

--phase 9 validation

Concepts used

- row-count verification
- schema validation
- metadata validation
- Delta read-back checks

Why this matters

- every load must be validated before promoting trust
- confirms data presence, schema correctness, and metadata completeness
- prevents silent failures entering Silver layer

Outcome

- verified Bronze correctness
- trusted ingestion layer
- ready handoff to Silver processing


How validation is implemented in this project

Main file:

- scripts/spark/validate_bronze.py

Pipeline support:

- run_pipeline.ps1 now supports RunBronzeValidation

What the validator checks

1. source row count

- reads the raw CSV source
- counts source rows

2. Bronze row count

- reads Bronze Delta table from path
- counts Bronze rows
- compares source count vs Bronze count

3. schema validation

- prints Bronze schema
- confirms table is readable

4. metadata validation

- checks these columns exist:
  - bronze_ingest_ts
  - bronze_source_file
  - bronze_batch_id
- checks required metadata columns are not null

5. Delta read-back validation

- reads Bronze Delta data successfully
- uses DESCRIBE DETAIL to inspect Delta metadata


How to run Phase 9 validation

Full Bronze load plus validation:

.\run_pipeline.ps1 -RunCsvToBronze -RunBronzeValidation -SkipBronzeToSilver

Validate selected Bronze tables only:

.\run_pipeline.ps1 -RunBronzeValidation -SkipBronzeToSilver -BronzeTables demographic enrolment


Validation passes when

- source_count = bronze_count
- Bronze schema is readable
- metadata columns exist
- metadata columns have no null values
- Delta read-back works


Bronze final deliverable in this project

- distributed raw storage in Delta format
- ACID-protected Bronze tables
- metadata and lineage for every load
- partitioned scalable design
- SQL-queryable Bronze catalog tables
- replayable ingestion pattern

--partitioning in a project

When to apply partitioning in any project

Apply partitioning when:

- table is large
- filtered queries are common
- same filter column is used again and again
- partition column has reasonable cardinality

Good partition columns:

- date
- year
- month
- low-cardinality status columns

Avoid partitioning on:

- user_id
- transaction_id
- pincode
- very high-cardinality columns

Simple rule:

Partition by columns used often in WHERE filters.
Do not create too many partitions.
Do not partition very small tables unnecessarily.


How partitioning is applied in this project

In this project, partitioning is applied at Delta write time.

Main files:

- scripts/spark/csv_to_delta.py
- scripts/spark/bronze_to_silver.py

Project partition strategy:

- Bronze fact-style tables partition by date
- Silver fact-style tables partition by date
- scheme_master_raw partitions by active_flag
- scheme_master_raw_valid partitions by active_flag

Why date was chosen:

- most tables are time-series style
- project grain is based on date + location
- date is commonly used for filtering
- date has much lower partition explosion than state + district + pincode

Why state/district/pincode were not chosen:

- too many folders
- too many small files
- slower metadata handling
- bad long-term scalability


General process to create partitioned Delta tables

1. Understand query pattern.
2. Identify the most common filter column.
3. Check cardinality of that column.
4. Choose a stable partition strategy.
5. Write Delta table with partitionBy.
6. Register the table in catalog if needed.
7. Validate partitioning using Spark SQL.


Minimal example

df.write.format("delta").partitionBy("date").mode("overwrite").save("/app/data/bronze/customers")


How it is done in this project

In csv_to_delta.py:

- partition strategy is stored in PARTITION_COLS_BY_TABLE
- date columns are normalized before writing
- writer.partitionBy(*partition_cols) is used before save

In bronze_to_silver.py:

- Silver uses the same partition strategy map
- partition columns are resolved table by table
- date partition column is normalized before write
- overwriteSchema is used to safely handle schema changes


Conceptual example

df.write.format("delta").partitionBy("date").save(path)

This creates folders like:

table/
  _delta_log/
  date=2025-03-01/
  date=2025-03-02/


How Spark uses partitioning

If query is:

SELECT * FROM bronze.demographic WHERE date = DATE '2025-03-01'

Spark can skip other date folders.
This is called partition pruning.


How to verify partitioning

In pyspark:

spark.sql("DESCRIBE DETAIL bronze.demographic").select("partitionColumns", "numFiles", "sizeInBytes").show(truncate=False)
spark.sql("SHOW PARTITIONS bronze.demographic").show(20, truncate=False)

spark.sql("DESCRIBE DETAIL silver.demographic_valid").select("partitionColumns", "numFiles", "sizeInBytes").show(truncate=False)
spark.sql("SHOW PARTITIONS silver.demographic_valid").show(20, truncate=False)

To check pruning:

spark.sql("EXPLAIN SELECT * FROM bronze.demographic WHERE date = DATE '2025-03-01'").show(truncate=False)


Important note

Changing code alone does not partition old data automatically.
Tables must be rewritten after partition logic is added.

In this project, after code change:

- rerun Bronze to recreate partitioned Bronze tables
- rerun Silver to recreate partitioned Silver tables


Final understanding

- partitioning is a physical storage optimization
- catalog is logical metadata
- Delta folder stores actual partitioned files
- metastore stores table registration

--phase 8 rerunnability design

Concepts used

- idempotent design patterns
- replay-safe ingestion
- controlled append strategy

Why this matters

- pipelines must recover from failures without manual cleanup
- reprocessing should not corrupt historical data
- reliable reruns are core production behavior

Outcome

- safe restart capability
- stable ingestion behavior under failures
- higher reliability in operations


How rerunnability is implemented in this project

Main files:

- scripts/spark/csv_to_delta.py
- scripts/spark/bronze_to_silver.py
- run_pipeline.ps1


Rerun-safe design used here

1. overwrite is the default mode

- Bronze default mode is overwrite
- Silver default mode is overwrite
- rerunning the same load replaces the table safely instead of duplicating data
- this makes full snapshot loads idempotent

2. targeted reruns are supported

- Bronze supports --tables
- Silver supports --tables
- if one table fails, only that table can be rerun
- no need to rerun the full pipeline every time

3. each pipeline run has a run id

- run_pipeline.ps1 generates RunId
- RunId is passed into Bronze logging
- RunId is passed into Silver load and stamped as silver_run_id
- this helps trace and replay specific runs

4. append mode is explicit and controlled

- append is not the default
- Bronze supports --mode append only when intentionally chosen
- append with --tables all is blocked by default
- this prevents accidental replay of the same full snapshot

5. catalog registration is safe to rerun

- CREATE DATABASE IF NOT EXISTS bronze
- CREATE TABLE IF NOT EXISTS bronze.<table>
- CREATE TABLE IF NOT EXISTS silver.<table>
- registration can be repeated without breaking the pipeline


New rerun controls added in this project

In run_pipeline.ps1:

- BronzeTables
- BronzeMode
- SilverTables
- SilverMode

Examples

Rerun only Bronze demographic with overwrite:

.\run_pipeline.ps1 -RunCsvToBronze -SkipBronzeToSilver -BronzeTables demographic -BronzeMode overwrite

Rerun only Bronze enrolment and biometric:

.\run_pipeline.ps1 -RunCsvToBronze -SkipBronzeToSilver -BronzeTables enrolment biometric

Rerun only Silver demographic and biometric:

.\run_pipeline.ps1 -SilverTables demographic biometric

Run full pipeline with normal safe overwrite:

.\run_pipeline.ps1 -RunCsvToBronze


Phase 8 design principle used here

For full snapshot sources:

- use overwrite
- make rerun replace the same logical data
- do not append the same full file again

For true incremental sources:

- use append carefully
- load only new files or new partitions
- always make append deliberate


Important lesson

- overwrite supports idempotent reruns for full extracts
- append is useful only for real incremental loads
- rerunnability is not only about code restart, it is also about preventing duplicate historical data
